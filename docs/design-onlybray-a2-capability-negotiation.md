# A2 — Bray 双端能力协商（onlyBray 分支设计）

状态：设计稿（待用户确认后实施）
分支：onlyBray
前置：无（独立设计，B3/B2/B1 均依赖它的协商结果）

## 1. 目标

双端都是 Bray 时，用一次轻量协商让双方确认"对端是自家内核 + 支持哪些私有扩展"，从而：
- 服务端可以启用/知道客户端支持的新格式（UDP 紧凑、下行分段…），不再做旧格式超集兼容的兜底判断；
- 客户端知道服务端支持哪些扩展后才切换私有路径，可安全回退。
识别面目标**不变**：传输仍伪装正常 HTTPS 站点。

## 2. 约束（硬性）

1. **零新增固定 header / query 名**——固定名字会被 DPI 统计成新特征。
2. **熵化**——能力信息必须藏在"本就随机的值"里（tokenish sessionId / padding），不可形成可识别特征。
3. **可回退**——老 Bray 客户端（无能力位）连新服务端正常；新客户端连老服务端也正常（探测到无回显 → 保守路径）。
4. **防伪造 / 防滥用**——能力位必须被会话 MAC 覆盖（对端确实持有 key 的自家客户端），不能被外部冒充或复用。

## 3. 载体（复用现有通道，不加新量）

- **客户端 → 服务端**：`sessionId` 里内嵌能力位（tokenish，base64url，本来就是随机值）；现有 `macVerifier.verify(sessionId)` / `verifySessionIDAny` 已覆盖 MAC，能力位天然防伪造。
- **服务端 → 客户端**：服务端**首个响应的 padding 值/头**回显"已确认 Bray + 能力掩码"；客户端在解析首个响应字节前不切换私有路径。

## 4. 能力位草案（首版，按需扩展）

| 位 | 名称 | 用途（后续 A/B/C 档挂载） |
|---|---|---|
| 0 | `udp-compact` | **B3** UDP 路径收紧（去掉旧单帧兜底字节） |
| 1 | `dseg` | **B1** 下行分段（段 GET 私有协议） |
| 2 | `pipeline` | **B2** 握手/首包合并管线化 |
| 3 | `batch` | A1 留位（批帧恢复；当前暂缓） |
| 4..7 | 保留 | 未来私有扩展 |

## 5. sessionId 内嵌方案（客户端 → 服务端）

现状：sessionId 长度可变、tokenish、带 MAC。方案：
- 客户端构造 sessionId 时，在随机部分之后追加 1 字节能力掩码（`0x80 | caps`，0x80 高位标记"Bray 能力域存在"），随后照常做 MAC。
- 服务端 `verifySessionIDAny` 解出后：
  - 无能力域（高位无）→ 老客户端，走保守路径；
  - 有能力域 → 校验通过（MAC 真、cap 真）→ 服务端记录"此会话=能力 X"，并在响应回显。
- 保持 MAC 长度/算法不变，仅扩展被 MAC 覆盖的字段。

## 6. 回显方案（服务端 → 客户端）

- 服务端首个响应的 padding 头/值里，把"确认掩码"放入（复用现有 `WriteResponseHeader` / XPadding 响应路径）。
- 客户端在**读取首个响应字节前**是保守路径；读到确认后，本连接/本会话启用被服务端确认的能力。

## 7. 安全考量

- 能力位被 MAC 覆盖 → 外部伪造/替换能力位会被校验拒绝。
- 能力掩码不含可枚举特征（随每会话随机 token 的形态）；高位标记本身不是固定 header/query。
- 回显不携带敏感信息，仅"能力确认"。

## 8. 测试计划

1. 单测：sessionId 编码/解码能力位 + 老格式兼容（无能力域）。
2. 单测：MAC 校验对"篡改能力位"拒绝。
3. 场景：新客户端↔新服务端 → 确认协商、走私有路径；新客户端↔老服务端（模拟无回显）→ 回退保守；老客户端↔新服务端 → 保守。
4. wire_audit：确认无新增固定 header/query 特征。

## 9. 后续挂载（B3/B2/B1）

- 拿到"能力确认"后各自实现，均以 `确认位为真 && 双方 Bray` 作为启用门禁，回退路径保留。
