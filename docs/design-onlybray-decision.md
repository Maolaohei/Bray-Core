# onlyBray 分支推进决策（2026-08-18）

按评审准绳（**性能 / 稳定性 / 抗GFW提升，无明确提升则不执行**）逐项判定：

## 已判定【移除】

- **A2 能力协商**：本身零提升（纯开关），不配独立实现。B1 需要的"客户端是否支持段协议"由**段 GET 自带的兼容标记**解决（见 B1 设计），不需要独立能力协商框架。设计稿 `design-onlybray-a2-capability-negotiation.md` 保留作参考，但不实施。
- **B3 UDP 路径总账**：每包省几字节、无识别面增益 → 不做。
- **B2 握手管线化**：现有 merge window（XRV 500ms / 非 XRV 50ms 先头+数据合并）已覆盖大半，增量极小 → 验证后若无明确增量不做。

## 已判定【推进】

- **B1 下行分段（M1）**：唯一明确提升项——
  - 识别面/传输形态：多段短 GET（HLS/DASH 视频分片形态）比"一条无限长 GET"更像真实 Web，**质的伪装提升**；
  - 稳定性：段可独立重试、断点续传，弱网下载更稳。
  实施顺序：
  1. 前置：双 GET ref-count（多下载腿共享 session 时，GET 完成不再立即删 session，引用计数归零才删）
  2. 段协议：GET+seq 段拉取（复用上行 seq 机制）
  3. 客户端段拉取（并发窗口 W + 重试）
  4. 服务端段缓存（24 段滑动缓存 + 上限）
  5. 全套测试（段路径 + 场景 + 弱网耐力）

- **C 档**：已评估全部不做（详见会话记录）。
